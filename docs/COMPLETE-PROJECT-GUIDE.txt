PART 1. WHAT THE PROJECT IS
=====================================================================================================
A backend (no screens) for an insurance company that handles motor and property claims.
You talk to it through Swagger UI, a web page that lets you call each API with a button.

THE BUSINESS STORY
  Before: customers phoned or emailed claims, nobody could see the status, staff used shared
          inboxes and spreadsheets, managers had no live view of money at risk.
  Now   : a customer creates a claim, an officer picks it up and reviews it, the claim is approved
          or rejected, approved claims are settled (paid). Managers see a live dashboard.

TECHNOLOGY
  Java 21, Spring Boot 3.4.5, Maven, Spring Data JPA, H2 database (in memory), Apache Kafka
  (optional), springdoc (Swagger UI), Spring Actuator, JUnit 5 + Mockito + MockMvc for tests.

THE FIVE BUILDING BLOCKS
  1. REST API      17 endpoints on port 8080.
  2. Database      H2 in memory. Tables CLAIMS and CLAIM_NOTES. Everything is LOST when the app stops.
  3. Lifecycle     ClaimTransitionValidator is the ONE class that decides which status changes are
                   allowed. Every status change in the project goes through it.
  4. Kafka         After key actions the app sends a message (an "event") to one of 5 topics. Nothing
                   in this project reads those messages yet. Kafka is optional.
  5. Swagger UI    http://localhost:8080/swagger-ui.html : where you test everything.

CODE LAYOUT (package com.chubb.claims)
  controller   receives HTTP requests, validates input, returns the response
  service      business rules (service/impl) and the lifecycle rules (service/workflow)
  repository   database queries (Spring Data JPA, including the dashboard counts and sums)
  entity       Claim, ClaimNote, ClaimStatus
  dto          request and response shapes (Java records)
  mapper       converts entity <-> response, and builds Kafka event messages
  exception    BusinessException, ResourceNotFoundException, GlobalExceptionHandler
  config       JPA auditing, Kafka setup, Swagger title
  kafka        ClaimEventProducer and the 5 event classes
  dashboard    manager dashboard and officer workload
  util         ClaimNumberGenerator (makes CLM-XXXXXXXXXXXX)

PART 3. THE COMPLETE FLOW OF A CLAIM (START TO END)
=====================================================================================================
THE LIFECYCLE (six statuses)

        create
          |
          v
        NEW --under-review--> UNDER_REVIEW --approve--> APPROVED --settle--> SETTLED (final)
                                 |    ^
                  request-more-info  |  additional-info (claimant)  or  under-review (officer)
                                 v    |
                           MORE_INFO_REQUIRED

        UNDER_REVIEW --reject--> REJECTED (final)

  Allowed moves (and nothing else):
      NEW                 -> UNDER_REVIEW
      UNDER_REVIEW        -> MORE_INFO_REQUIRED, APPROVED, REJECTED
      MORE_INFO_REQUIRED  -> UNDER_REVIEW
      APPROVED            -> SETTLED
      REJECTED, SETTLED   -> nothing (final: no edits, no reassigning, no moves; notes still allowed)
  Any other move returns HTTP 409 with a message such as:
      Invalid status transition: NEW -> APPROVED. Allowed from NEW: [UNDER_REVIEW]

  "OPEN" claims = NEW, UNDER_REVIEW, MORE_INFO_REQUIRED. (APPROVED is waiting for payment and is
  NOT counted as open on the dashboard.)

THE STORY, STEP BY STEP, WITH WHO DOES WHAT
  1. CLAIMANT   reports the incident:  POST /api/claims         -> claim is NEW, gets a claim number.
                                                                  Event sent: claim-created.
  2. OFFICER    looks at the inbox:    GET /api/claims?status=NEW
  3. OFFICER    takes the claim:       PUT /api/claims/{id}/assign        Event: claim-assigned.
  4. OFFICER    starts the review:     PUT /api/claims/{id}/under-review  NEW -> UNDER_REVIEW.
  5. OFFICER    writes notes:          POST /api/claims/{id}/notes
  6. (if something is missing)
     OFFICER    asks the customer:     PUT /api/claims/{id}/request-more-info   -> MORE_INFO_REQUIRED
     CLAIMANT   sees the status and the question (GET claim, GET notes), then answers:
                                       POST /api/claims/{id}/additional-info    -> UNDER_REVIEW again
     (this loop can repeat)
  7. OFFICER    decides:
        approve: PUT /api/claims/{id}/approve  -> APPROVED          Event: claim-approved
                 PUT /api/claims/{id}/settle   -> SETTLED (paid)    Event: claim-settled
        reject : PUT /api/claims/{id}/reject   -> REJECTED          Event: claim-rejected
                 (put the reason in the note; it is saved and sent in the event as "reason")
  8. CLAIMANT   checks the outcome:    GET /api/claims/{id}  or  GET /api/claims/claim-number/{n}
  9. OFFICER    checks own workload:   GET /api/officers/{officer}/workload
 10. MANAGER    checks the team:       GET /api/dashboard/workload

WHAT HAPPENS INSIDE ONE REQUEST (example: approve)
  PUT /api/claims/1/approve
    1. ClaimWorkflowController receives it.
    2. The service loads the claim from the database (HTTP 404 if there is none).
    3. ClaimTransitionValidator checks UNDER_REVIEW -> APPROVED is allowed (HTTP 409 if not).
    4. Status is changed, the optional note is saved, the claim is saved: ONE database transaction.
    5. AFTER the transaction is committed, the event is sent to Kafka (so a failed request never
       produces an event). If Kafka is down, only a log line is written; the API call still succeeds.
    6. The answer is wrapped in {success, message, data}. Any error becomes the same format via
       GlobalExceptionHandler (400, 404, 409, 500).

PART 4. ROLES: WHO THEY ARE AND HOW THEY WORK
=====================================================================================================
THREE ROLES
  CLAIMANT (the customer)
     Wants to: report an incident, see the status, send extra information when asked.
     Uses    : POST /api/claims, GET /api/claims/{id}, GET /api/claims/claim-number/{n},
               GET /api/claims/{id}/notes, POST /api/claims/{id}/additional-info
     Learns the result by reading the claim status (there is no email or push message yet).

  CLAIMS OFFICER (staff)
     Wants to: see incoming claims, take ownership, review, ask questions, decide, pay, see own load.
     Uses    : GET /api/claims (inbox, filters), PUT assign, PUT under-review, POST/GET notes,
               PUT request-more-info, PUT approve, PUT reject, PUT settle,
               GET /api/officers/{officer}/workload

  MANAGER
     Wants to: see team workload, claims by status, total money at risk.
     Uses    : GET /api/dashboard/workload, GET /api/claims?status=...

  PUT /api/claims/{id} (update) and DELETE /api/claims/{id} are not given to any role in the project
  brief. Treat them as back-office actions.

WHO IS MEANT TO CALL WHAT  (C = claimant, O = officer, M = manager)
  POST   /api/claims                                  C
  GET    /api/claims/{id}  and  /claim-number/{n}     C  O  M
  GET    /api/claims                                  O  M
  GET    /api/claims/{id}/notes                       C  O      (claimant use is an addition: it is how
                                                                 they see what the officer asked)
  PUT    /api/claims/{id}/assign                         O
  PUT    /api/claims/{id}/under-review                   O
  POST   /api/claims/{id}/notes                          O
  PUT    /api/claims/{id}/request-more-info              O
  POST   /api/claims/{id}/additional-info             C
  PUT    /api/claims/{id}/approve | reject | settle      O
  GET    /api/officers/{officer}/workload                O
  GET    /api/dashboard/workload                            M

IMPORTANT TRUTH: ROLES ARE NOT ENFORCED                                                   [VERIFIED]
  - There is NO login, NO token, NO permission check. The project does not use Spring Security.
  - The roles above are a CONVENTION: who is supposed to use which API. The server does not check who
    is calling. Any caller can call any API.
  - Proof: a "claimant" calling PUT /api/claims/3/approve on their own claim gets HTTP 200 and the
    claim becomes APPROVED (step 55 of Part 9).
  - The only rules enforced are about the CLAIM STATUS (for example approve only works on an
    UNDER_REVIEW claim), never about the caller.
  - The "officer" is only a text name stored on the claim. There is no user account, and nothing checks
    that the name exists.
  - In Swagger you play a role simply by choosing that role's APIs. There is no Authorize button.
  - Planned (not built): OAuth2 login, claimant/officer/manager roles, claimants limited to their own
    claims. See docs/architecture.md, "Future enhancements".

HOW TO CALL AN API IN SWAGGER
  1. Click the API row to open it.        2. Click "Try it out".
  3. Fill in the id / parameters / body.  4. Click "Execute".
  5. Read "Server response": the Code, and the Response body. Compare with the "Expect" line.

THREE THINGS THAT WILL TRICK YOU
  1. LIST CLAIMS (GET /api/claims) RETURNS 500 IF YOU JUST CLICK EXECUTE.                  [VERIFIED]
     Swagger shows one box called "pageable" pre-filled with
         {"page":1073741824,"size":1073741824,"sort":["string"]}
     "string" is not a real field, so the server fails with HTTP 500 "An unexpected error occurred".
     FIX: replace the whole box with   {"page":0,"size":20}
     (confirmed in the real Swagger UI: this sends ?page=0&size=20 and returns 200).
     To sort:  {"page":0,"size":2,"sort":["createdAt,desc"]}

  2. THE WORKFLOW APIs PRE-FILL THE BODY WITH {"note":"string"}.                           [VERIFIED]
     (under-review, request-more-info, approve, reject, settle) The body is optional. If you leave
     it, a real note with the text "string" is saved on the claim.
     FIX: type a real note, or replace the body with   {}

  3. WITHOUT KAFKA, WRITE CALLS ARE SLOW.                                                  [VERIFIED]
     Create, assign, approve, reject and settle take about 5 to 6 seconds. The result is still
     correct. Wait for the response before clicking again.

ALSO
  - Restart the app before a full test run: data lives in memory, so ids start again at 1.
  - Names with a space (John Smith) are encoded by Swagger automatically. Type them normally.
  - Dates are yyyy-MM-dd (example 2026-09-15). The date must not be in the future.

PART 6. RESPONSE FORMAT, STATUS CODES AND ERROR MESSAGES
=====================================================================================================
THE ENVELOPE  (all claim, note and workflow APIs)
      { "success": true,  "message": "Claim created successfully", "data": { ... } }
      { "success": false, "message": "Validation failed",          "data": { "field": "message" } }
  Fields that are empty (null) are left out of the JSON (for example assignedOfficer before a claim is
  assigned, and "data" on delete).
  EXCEPTION: the two dashboard APIs return plain JSON without success/message/data.

CLAIM OBJECT (inside "data")
      id, claimNumber, claimantName, claimantEmail, policyNumber, description, incidentDate,
      claimAmount, liabilityExposure, status, assignedOfficer (only when assigned), createdAt, updatedAt

PAGE OBJECT (inside "data" of the list API)
      content [ claims ], page (0-based), size, totalElements, totalPages

NOTE OBJECT
      id, claimId, note, createdAt

STATUS CODES
  200  OK
  201  Created (create claim, add note)
  400  Validation failed (data lists each wrong field) or "Malformed request" (broken JSON, wrong type,
       bad date, bad enum such as status=FOO, text where a number is expected)
  404  Claim not found
  405  Method not supported
  409  Business rule broken: invalid status change, claim is final (edit/assign), or two people changed
       the claim at the same moment ("The claim was modified concurrently, please retry")
  500  Unexpected error (details only in the log)

EXACT MESSAGES YOU WILL SEE
  404  Claim not found with id: 9999
  404  Claim not found with claim number: CLM-DOESNOTEXIST
  409  Invalid status transition: NEW -> APPROVED. Allowed from NEW: [UNDER_REVIEW]
  409  Invalid status transition: SETTLED -> UNDER_REVIEW. Allowed from SETTLED: []
  409  Additional information can only be submitted while the claim is MORE_INFO_REQUIRED (current: NEW)
  409  Claim 1 can no longer be edited (status: SETTLED)
  409  Claim 1 cannot be assigned because it is SETTLED
  400  Validation failed          (with data: { "claimantName": "claimantName is mandatory", ... })
  400  Malformed request
  500  An unexpected error occurred

Each API below shows: who uses it, what it does, what you send, when it works, what it changes, what

VALIDATION RULES USED BY SEVERAL APIs (claim fields)
  claimantName       required, not blank, max 150 characters
  claimantEmail      required, must be a valid email, max 150 characters

  description        required, not blank, max 2000 characters

  claimAmount        required, greater than 0, up to 13 digits before and 2 after the decimal point
  liabilityExposure  required, greater than 0, same digit rule

-----------------------------------------------------------------------------------------------------
API 1.  POST /api/claims               CREATE A CLAIM
-----------------------------------------------------------------------------------------------------
  Who         : Claimant
  What it does: Creates a new claim with status NEW and a generated claim number (CLM- plus 12
                letters/digits, for example CLM-AEB9543816E1). No officer is assigned yet.
  Send (body) : claimantName, claimantEmail, policyNumber, description, incidentDate, claimAmount,
                liabilityExposure   (rules above)
  Works when  : always
  Changes     : inserts one row in CLAIMS.
  Event       : claim-created (after commit).
  Success     : 201 Created, header Location: /api/claims/{id},
                message "Claim created successfully", data = the claim (status NEW).
  Errors      : 400 Validation failed (one message per wrong field)
                400 Malformed request (broken JSON, bad date, text in a number field)
  Example body:
      {
        "claimantName": "Asha Verma",
        "claimantEmail": "asha.verma@example.com",
        "policyNumber": "POL-100234",
        "description": "Rear-end collision at traffic signal, bumper and boot damage",
        "incidentDate": "2026-09-15",
        "claimAmount": 45000.00,
        "liabilityExposure": 30000.00
      }
  Real response [VERIFIED]:
      {"success":true,"message":"Claim created successfully","data":{"id":1,"claimNumber":"CLM-AEB9543816E1",
       "claimantName":"Asha Verma","claimantEmail":"asha.verma@example.com","policyNumber":"POL-100234",
       "description":"Rear-end collision at traffic signal, bumper and boot damage","incidentDate":"2026-09-15",
       "claimAmount":45000.00,"liabilityExposure":30000.00,"status":"NEW",
       "createdAt":"2026-10-22T17:18:26.5374835","updatedAt":"2026-10-22T17:18:26.5374835"}}
  Wrong-input response [VERIFIED] (body with every field wrong):
      400  {"success":false,"message":"Validation failed","data":{"description":"description is mandatory",
           "claimantName":"claimantName is mandatory","claimantEmail":"claimantEmail must be a valid email address",
           "claimAmount":"claimAmount must be greater than 0","incidentDate":"incidentDate cannot be in the future",
           "liabilityExposure":"liabilityExposure must be greater than 0","policyNumber":"policyNumber is mandatory"}}
  curl:
      curl -X POST http://localhost:8080/api/claims -H 'Content-Type: application/json' -d '{"claimantName":"Asha Verma","claimantEmail":"asha.verma@example.com","policyNumber":"POL-100234","description":"Rear-end collision","incidentDate":"2026-09-15","claimAmount":45000.00,"liabilityExposure":30000.00}'
  Tested in Part 9: steps 1, 2, 3, 4 (success), 32, 33, 34 (errors)

-----------------------------------------------------------------------------------------------------
API 2.  GET /api/claims                LIST CLAIMS (PAGED, WITH FILTERS)
-----------------------------------------------------------------------------------------------------
  Who         : Officer (the inbox), Manager
  What it does: Returns claims a page at a time, newest first by default.
  Send (query): status           NEW | UNDER_REVIEW | MORE_INFO_REQUIRED | APPROVED | REJECTED | SETTLED
                assignedOfficer  exact officer name
                policyNumber     exact policy number
                pageable         in Swagger a JSON box, use {"page":0,"size":20}   (see Part 5)
                (outside Swagger: ?page=0&size=20&sort=createdAt,desc)
  FILTER RULE : only ONE filter is applied. Order of priority: status, then assignedOfficer, then
                policyNumber. If you send status and assignedOfficer together, only status is used.
                No filter = all claims. Blank text filters are ignored.
  Default     : 20 per page, sorted by createdAt descending (newest first).
  Works when  : always. Changes nothing. No event.
  Success     : 200, message "Claims retrieved successfully",
                data = {content:[...], page, size, totalElements, totalPages}
  Errors      : 400 Malformed request (status=FOO)
                500 if "sort" names a field that does not exist, for example sort=string (known issue,
                    Part 16). This is what Swagger's untouched default box sends.
  Real response [VERIFIED] (status=NEW, one claim):
      {"success":true,"message":"Claims retrieved successfully","data":{"content":[{"id":4,...,"status":"NEW",...}],
       "page":0,"size":20,"totalElements":1,"totalPages":1}}
  curl:
      curl 'http://localhost:8080/api/claims?status=NEW&page=0&size=20'
      curl 'http://localhost:8080/api/claims?assignedOfficer=John%20Smith&page=0&size=20'
      curl 'http://localhost:8080/api/claims?policyNumber=POL-200567&page=0&size=20'
  Tested in Part 9: steps 22, 23, 24, 25, 26, 27 (success), 39 (error)

-----------------------------------------------------------------------------------------------------
API 5.  PUT /api/claims/{id}           UPDATE CLAIM DETAILS
-----------------------------------------------------------------------------------------------------
  Who         : back office (no role assigned in the brief)
  What it does: Replaces claimantName, claimantEmail, description, incidentDate, claimAmount and
                liabilityExposure. The policy number, claim number, status and officer are NOT changed.
  Send        : path id + body with the six fields (same rules as create, but no policyNumber)
  Works when  : status is NEW, UNDER_REVIEW, MORE_INFO_REQUIRED or APPROVED.
                Refused when REJECTED or SETTLED (final).
  Changes     : updates the CLAIMS row (and its version number). No event. Status does not change.
  Success     : 200, message "Claim updated successfully", data = the updated claim

=====================================================================================================
GROUP C: CLAIM WORKFLOW  (Swagger tag "Claim Workflow")
=====================================================================================================
These six APIs move the claim along its lifecycle. They all work the same way:
  - Optional body {"note": "..."} (max 4000). A non-blank note is saved as a ClaimNote.
    Leave the body out or send {} for no note. (In Swagger replace the pre-filled "string".)
  - They check the move with ClaimTransitionValidator. A wrong move returns 409 and changes nothing.
  - Common errors: 404 Claim not found, 409 Invalid status transition: A -> B. Allowed from A: [...]
  - Status change, note and save happen in one transaction.

-----------------------------------------------------------------------------------------------------
API 10. PUT /api/claims/{id}/under-review     START (OR RESTART) THE REVIEW
-----------------------------------------------------------------------------------------------------
  Who         : Officer
  Moves       : NEW -> UNDER_REVIEW, or MORE_INFO_REQUIRED -> UNDER_REVIEW
  Success     : 200, message "Claim moved to review", status UNDER_REVIEW
  Event       : none
  409 example : Invalid status transition: SETTLED -> UNDER_REVIEW. Allowed from SETTLED: []
  curl        : curl -X PUT http://localhost:8080/api/claims/1/under-review -H 'Content-Type: application/json' -d '{"note":"Starting review"}'
  Tested in Part 9: steps 10, 15, 21 (success), 49 (409)

-----------------------------------------------------------------------------------------------------
API 11. PUT /api/claims/{id}/request-more-info   ASK THE CLAIMANT FOR INFORMATION
-----------------------------------------------------------------------------------------------------
  Who         : Officer
  Moves       : UNDER_REVIEW -> MORE_INFO_REQUIRED
  Success     : 200, message "More information requested", status MORE_INFO_REQUIRED
  Event       : none. The claimant is NOT notified: they must look at the claim. Put the question in
                the note, it is saved on the claim where the claimant can read it (API 9).
  409 example : Invalid status transition: NEW -> MORE_INFO_REQUIRED. Allowed from NEW: [UNDER_REVIEW]
  curl        : curl -X PUT http://localhost:8080/api/claims/2/request-more-info -H 'Content-Type: application/json' -d '{"note":"Please send plumber invoice and photos"}'
  Tested in Part 9: step 16 (success), 45 (409)

=====================================================================================================
PART 8. DATA MODEL (DATABASE TABLES AND RULES)
=====================================================================================================
TABLE CLAIMS
  ID                  number, automatic, primary key
  CLAIM_NUMBER        text (32), unique, never changes     example CLM-AEB9543816E1
  CLAIMANT_NAME       text (150), required
  CLAIMANT_EMAIL      text (150), required, valid email
  POLICY_NUMBER       text (50), required (indexed)
  DESCRIPTION         text (2000), required
  INCIDENT_DATE       date, required, not in the future
  CLAIM_AMOUNT        decimal(15,2), required, greater than 0
  LIABILITY_EXPOSURE  decimal(15,2), greater than 0 (via the API)
  STATUS              text: NEW, UNDER_REVIEW, MORE_INFO_REQUIRED, APPROVED, REJECTED, SETTLED (indexed)
  ASSIGNED_OFFICER    text (150), empty until assigned (indexed)
  CREATED_AT          set automatically when created
  UPDATED_AT          set automatically on every change
  VERSION             counter, +1 on every change (used for "optimistic locking", see Glossary)

TABLE CLAIM_NOTES
  ID                  number, automatic
  CLAIM_ID            the claim this note belongs to (required, indexed)
  NOTE                text (4000), required
  CREATED_AT          set automatically
  Deleting a claim deletes its notes. Notes are never edited or deleted on their own.

PART 12. HOW THE CODE WORKS INSIDE
=====================================================================================================
CONTROLLERS (HTTP only)
  ClaimController           API 1 to 6          /api/claims
  ClaimOfficerController    API 7, 8, 9         /api/claims/{id}/assign, /notes
  ClaimWorkflowController   API 10 to 15        /api/claims/{id}/under-review ... /settle, /additional-info
  DashboardController       API 16              /api/dashboard/workload
  OfficerWorkloadController API 17              /api/officers/{officer}/workload

SERVICES (business rules)
  ClaimServiceImpl            create, read, list, update, delete
  ClaimAssignmentServiceImpl  assign; refuses final claims
  ClaimNoteServiceImpl        add and list notes
  ClaimWorkflowServiceImpl    ONE private method transition(): load claim, check rule, set status,
                              save optional note, save claim, send event. All six workflow APIs use it.
  DashboardServiceImpl        calls the repository counts and fills in missing statuses with 0

THE RULE BOOK: ClaimTransitionValidator
  A map of "from status -> allowed next statuses". The only place lifecycle rules exist. To change a
  rule you change one line. It also says which statuses are final (REJECTED, SETTLED).

DASHBOARD QUERIES (ClaimRepository)
  Open count and exposure : where status in (NEW, UNDER_REVIEW, MORE_INFO_REQUIRED)
  Claims by status        : group by status over ALL claims
  Claims per officer      : open claims grouped by assignedOfficer, busiest first, unassigned excluded
  Officer workload        : the same, filtered to one officer
  All numbers come from the database (count / sum / group by), no claim rows are loaded.

OPTIMISTIC LOCKING
  The VERSION column. If two people change the same claim at the same moment, the second one fails
  with 409 "The claim was modified concurrently, please retry" instead of silently overwriting.

ERROR HANDLING
  GlobalExceptionHandler turns every exception into the {success:false, message, data} format:
  ResourceNotFoundException -> 404, BusinessException -> 409, optimistic-lock failure -> 409,
  validation errors -> 400 with field messages, bad JSON / wrong type -> 400, unknown URL -> 404,
  anything else -> 500 "An unexpected error occurred" (the real error is only in the log).

CONFIGURATION (src/main/resources/application.properties)
  server.port=8080, H2 in memory (jdbc:h2:mem:claimsdb), ddl-auto=update (tables built from entities),
  Kafka at ${KAFKA_BOOTSTRAP_SERVERS:localhost:9092}, topic names app.kafka.topics.*, springdoc paths,
  actuator exposes health, info, metrics. Logs: console + logs/claims-management.log.


=====================================================================================================
PART 13. KAFKA EVENTS
=====================================================================================================
WHAT IS IT FOR
  Other systems (email, reporting) can react to claim decisions without slowing the API. In this
  project the app only SENDS the messages; nothing reads them, so nobody is emailed yet.

TOPICS (3 partitions each, created at startup when Kafka is running)
  Topic            Sent by                       Key           Extra content
  claim-created    POST /api/claims              claim number  policy, claimant name/email, amounts, status
  claim-assigned   PUT .../assign (every time)   claim number  assignedOfficer, status
  claim-approved   PUT .../approve               claim number  policy, claimant email, amounts, officer
  claim-rejected   PUT .../reject                claim number  policy, claimant email, officer, reason (the note)
  claim-settled    PUT .../settle                claim number  policy, claimant email, claimAmount, officer
  Every message also has eventId (unique), claimId, claimNumber, occurredAt (ISO time).
  Empty fields are left out. Using the claim number as key keeps all events of one claim in order.
  under-review, request-more-info, additional-info, notes, update and delete send NOTHING.

WHEN IS THE MESSAGE SENT
  After the database transaction is committed. A request that fails never produces an event.
  Sending is "best effort": if Kafka is down the failure is logged ("Failed to publish ...") and the
  API call still succeeds (but waits up to 5 seconds).

EXPECTED MESSAGE COUNT after steps 1 to 19 on a fresh broker
  claim-created 4, claim-assigned 3, claim-approved 1, claim-settled 1, claim-rejected 1

HOW TO SEE THE MESSAGES (needs Docker)                                                    [NOT RUN]
      docker compose up -d                       (before starting the app)
      docker exec -it claims-kafka /opt/kafka/bin/kafka-console-consumer.sh --bootstrap-server localhost:9092 --topic claim-approved --from-beginning --property print.key=true
  Replace claim-approved with any topic above.
  Docker is not installed on the machine used for this guide, so these exact commands were not run.
  The same topics and messages ARE checked by the automated test ClaimLifecycleIntegrationTest, which
  uses a built-in Kafka broker and PASSED (Part 14).

PART 16. KNOWN LIMITATIONS AND FINDINGS (be upfront about these)
=====================================================================================================
  1. NO AUTHENTICATION OR ROLES. Any caller can call any API (step 55). Planned: OAuth2 roles.
  2. INVALID SORT RETURNS 500, NOT 400. GET /api/claims with sort=string (Swagger's untouched default
     box) fails with "An unexpected error occurred" because an unknown field name surfaces as an
     unhandled error. Easy to fix by mapping it to 400.
  3. DELETE HAS NO STATUS CHECK. A claim can be deleted in any status, even SETTLED, with its notes.
  4. UPDATE IS ALLOWED ON APPROVED CLAIMS (refused only on REJECTED and SETTLED), so amounts of an
     approved claim can still be edited.
  5. ASSIGN IS INDEPENDENT OF STATUS. Nothing forces assigning before review. It also does not change
     the status.
  6. THE OFFICER IS ONLY A NAME (text). No officer record; spelling differences create "different"
     officers on the dashboard.
  7. NO ONE READS THE KAFKA EVENTS. No emails are sent when a claim is approved or rejected.
  8. EVENTS ARE BEST EFFORT. One can be lost if the app stops right after a database commit. (Planned
     fix: a transactional outbox.)
  9. APPROVED CLAIMS ARE NOT "OPEN". Their money is not in the dashboard exposure (this follows the
     project brief; it is a business question).
 10. ONLY ONE LIST FILTER APPLIES (status, then officer, then policy).
 11. IN-MEMORY DATABASE: H2 keeps everything in memory, so all data is lost on restart.
 12. SWAGGER DEFAULTS CAN HURT: the "pageable" box (500) and the pre-filled note "string" (Part 5).
 13. DASHBOARD RETURNS BARE JSON while all other APIs use the {success,message,data} envelope.

PART 18. GLOSSARY (PLAIN-ENGLISH WORDS)
=====================================================================================================
  API / endpoint     One address you can call, such as POST /api/claims. This project has 17.
  Swagger UI         A web page that lists every API and lets you call it with buttons.
  HTTP method        GET = read, POST = create, PUT = change, DELETE = remove.
  Status code        200 OK, 201 Created, 400 your input is wrong, 404 not found, 409 conflict with the
                     rules, 500 server error.
  Request body       The JSON you send. Response body: the JSON you get back.
  Envelope           The wrapper {success, message, data} around responses.
  Claim              One insurance claim. Claim number = the public id (CLM-...). id = the database id.
  Status             Where the claim is in its life: NEW, UNDER_REVIEW, MORE_INFO_REQUIRED, APPROVED,
                     REJECTED, SETTLED.
  Transition         A move from one status to another. Only the allowed ones work.
  Final status       REJECTED or SETTLED: the claim can no longer change.
  Open claim         NEW, UNDER_REVIEW or MORE_INFO_REQUIRED.
  Liability exposure The amount of money the insurer could have to pay on the claim.
  Officer            The staff member handling a claim (only a name here).
  Note               A text comment saved on a claim. Notes also record decisions and customer answers.
  Dashboard          Live numbers for managers: open claims, money at risk, claims by status/officer.
  H2                 A small database that runs inside the app, in memory, wiped on restart.
  JPA / Hibernate    The tool that saves Java objects as database rows.
  Transaction        A group of database changes that all succeed or all fail together.
  Optimistic locking A VERSION counter that stops two people silently overwriting each other.
  Kafka              A message system. The app drops a message ("event") on a topic after key actions.
  Topic              A named mailbox in Kafka (claim-created, claim-assigned, ...).
  Event              One message describing something that happened (for example "claim approved").
  Event after commit The message is sent only once the database change is safely saved.
  Role               Claimant, officer or manager. Here only a convention, not enforced.
  Mock / MockMvc     Test tools that call the code without starting a real server.
